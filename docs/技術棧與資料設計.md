# 菜就多煉：技術棧與資料設計

## 建議技術棧

| 層次 | 建議 | 理由 |
|---|---|---|
| 後端 API | 原型使用 Python `http.server`；擴充時可改 FastAPI | 目前原型用標準函式庫提供本機 API，不需額外安裝套件；食譜搜尋、條件比對與排序留在可驗證的程式規則中。 |
| 資料庫 | SQLite | 單一資料庫檔案、無需額外資料庫伺服器，適合此專題規模與本機展示。Python 的 `sqlite3` 可直接連線，不必先加入 ORM。 |
| 前端（後續階段） | HTML、CSS、原生 JavaScript | 簡單頁面不必先引入大型框架；以 `fetch` 呼叫 API。這次不建立完整前端。 |
| 資料交換 | JSON | API 回應使用 JSON；資料庫仍用關聯式表格及外鍵維持一致性。 |
| 食譜推薦 | SQL 檢索 + 明確比對規則 | 以現有食譜資料、使用者勾選、器具適用性和偏好分數排序；不使用 AI 即時生成食譜。 |

SQLite 是單檔、免獨立伺服器的資料庫；Python 標準函式庫提供 `sqlite3` 介面。這個原型以 `http.server` 簡化本機啟動流程；若日後擴充為多人使用的 API，再導入 FastAPI 等框架。[SQLite](https://www.sqlite.org/about.html) [Python sqlite3](https://docs.python.org/3/library/sqlite3.html) [FastAPI](https://fastapi.tiangolo.com/)

### 何時再升級

若之後需要多人同時大量寫入、雲端部署或正式帳號管理，再評估 PostgreSQL、資料遷移工具與登入機制。現階段先不加上 ORM、Redis、AI API 或大型前端框架，以免增加設定負擔。

## 類別圖與資料表對應

原始 UML 類別圖包含「使用者、個人偏好設定、食譜、食材、調味料、推薦比對模組」。本資料模型保留這些概念，並將清單拆成關聯表：

- 使用者與個人偏好設定：`users`、`personal_settings`（一對一）。
- 使用者常備器具：`equipment`、`user_equipment`（多對多）；食譜需求亦使用 `recipe_equipment`。
- 食譜及組成：`recipes`、`recipe_ingredients`、`recipe_seasonings`、`recipe_steps`。
- 替代食材：`ingredient_substitutions`。
- 收藏：`recipe_favorites`（以使用者與食譜的複合主鍵避免重複收藏）、`favorite_folders`（使用者自訂分類資料夾）。
- 一次搜尋的選取條件：`search_requests` 及其食材、調味料、器具關聯表。
- 推薦比對模組是執行資料庫檢索及排序的應用邏輯，不是另一張資料表；排序規則應固定、可說明、可重現。

## F01–F13 對應

| 需求 | 資料支援 |
|---|---|
| F01 個人口味 | `personal_settings.taste_level`、`eats_spicy`、`default_servings`；推薦與調味份量計算讀取這些欄位。 |
| F02 烹飪器具 | `equipment`、`user_equipment` 儲存器具目錄及使用者常備器具。 |
| F03 查詢食材清單 | `ingredients` 以名稱、分類、別名查詢；`seasonings` 以名稱、分類查詢。 |
| F04 選擇現有食材 | `search_request_ingredients` 保存單次搜尋所勾選的食材。 |
| F05 選擇現有調味料 | `search_request_seasonings` 保存單次搜尋所勾選的調味料。 |
| F06 選擇料理類型 | `search_requests.cuisine_filter` 支援 `any`、`chinese`、`western`。 |
| F07 食譜條件比對 | 比對搜尋條件與食譜組成表；器具需求按 `requirement_group` 分組，每組可用一件符合器具。 |
| F08 推薦結果排序 | 根據必要食材符合度、調味料齊全度、器具適用性計算可解釋分數；分數屬執行時計算，不寫死在食譜資料。 |
| F09 顯示缺少材料 | `recipe_ingredients.is_required`、`recipe_seasonings.is_required` 區分必要與可省略項目；與搜尋勾選清單差集即為缺料。 |
| F10 食譜詳細資訊 | 食譜、食材、調味料、器具及步驟分別存放並以外鍵關聯。 |
| F11 精準調味建議 | 基礎份量、文字十進位數量、單位與偏好設定可供後端以 `Decimal` 計算。克與體積互換須有對應品項的可靠密度；資料不足就不換算。茶匙及湯匙以 5 mL 與 15 mL 為體積基準。 |
| F12 食材替代建議 | `ingredient_substitutions` 明確記錄原食材、替代食材及適用說明；無登錄即不建議。 |
| F13 收藏食譜 | `recipe_favorites` 儲存使用者與食譜的對應及所屬資料夾，`favorite_folders` 支援自訂分類。 |

## 用量與精度

`quantity_value` 與 `grams_per_ml` 使用文字欄位保存十進位字串，應用程式讀取後用 Python `Decimal` 計算，避免先轉成二進位浮點數。食譜保留原始數量和單位。體積單位間可依 1 tsp = 5 mL、1 tbsp = 15 mL 換算；重量與體積之間只有在該品項有經確認的密度資料時才顯示換算值。測試資料未提供經查證的密度，因此不假設克數與毫升可互換。

建議份量與口味計算：先以 `原始用量 × 目標份數 ÷ 食譜基礎份數` 換算份量；若該調味列 `taste_adjustable = 1`，再乘口味係數（初版可採清淡 0.8、適中 1.0、重口味 1.2，之後由實際試做調整）。只在最後顯示時依單位設定精度，不覆寫資料庫原始用量。辣味開關應只影響資料中明確標示為辣味的項目；食譜未含辣味材料時不額外添加。

## 建置資料庫

使用 Python 內建 `sqlite3` 執行 `database/schema.sql`，再執行 `database/seed.sql`。兩個 SQL 檔均設定外鍵；食譜資料的用量是示範資料，實際料理前仍應由專題成員覆核。

## RecipeMatcher

`database/recipe_matcher.py` 提供 `RecipeMatcher`。呼叫端傳入勾選的食材、調味料及器具資料表 ID，以及料理類型；若省略器具 ID 並提供 `user_id`，就套用該使用者已保存的器具。口味、是否吃辣與預設份數也從 `personal_settings` 讀取，可用參數覆寫以預覽不同偏好。

推薦分數固定滿分 100：必要食材 60 分、必要調味料 20 分、器具適用性 20 分。缺少必要食材但有已登錄且目前持有的替代食材時，該項以 75% 權重計分；否則該項不計分。器具依 `requirement_group` 檢查：同一組擇一符合，所有組都符合才得到器具分。排序同分時優先原食材齊全、必要調味料較齊、烹飪時間較短的食譜。結果仍包含器具不適用項目並明確標示，方便使用者看到原因及替代條件。

使用範例：

```python
from database.recipe_matcher import RecipeMatcher

with RecipeMatcher.from_path("data/菜就多煉.sqlite3") as matcher:
    results = matcher.match(
        user_id="demo-user",
        available_ingredient_ids=[1, 2, 3, 4],
        available_seasoning_ids=[1, 2, 5],
        cuisine_filter="chinese",
        servings=3,
    )
```

用量先以目標份數／基礎份數縮放；`taste_adjustable` 為真時再套用清淡 0.8、適中 1.0、重口味 1.2。是否吃辣由調味料的 `is_spicy` 控制：不吃辣時該項用量為 0，且不會被當成缺少調味料。茶匙、湯匙、毫升之間按 5 mL／15 mL 換算；克數與體積只有在該調味料 `density_quality = 'verified'` 且有 `grams_per_ml` 時才互換。內部用 `Decimal` 計算，回傳顯示值才四捨五入至 0.001 單位。

## 分鏡板 UI 與啟動

`web/static/` 實作手機優先的響應式介面，流程對應分鏡板：個人設定、食材／調味料／料理類型選擇、推薦結果、食譜詳情，以及可建立資料夾的收藏頁。中文食材搜尋只更新結果清單，不重建輸入框，以免打斷注音或其他中文輸入法的組字。

在專案根目錄啟動本機介面：

```powershell
python web/server.py
```

再以瀏覽器開啟 `http://127.0.0.1:8000`。伺服器只監聽本機迴圈位址。個人設定、器具、收藏與資料夾會寫入 SQLite；食譜搜尋使用既有 `RecipeMatcher`。

## 驗證

從專案根目錄執行：

```powershell
python database/build_db.py --force
python -m unittest discover -s tests -v
```

`build_db.py --force` 會以測試種子資料重建並覆寫 SQLite 檔；若資料庫已有自己的收藏或修改，不要執行此重建指令。單獨執行測試時，測試會使用記憶體資料庫，不會更動 `data/菜就多煉.sqlite3`。

測試涵蓋完整材料的排序、缺少青江菜時以現有菠菜提示替代、不適用氣炸鍋的器具標記、清淡口味份量調整、吃辣與不吃辣的辣椒粉處理、份量縮放、茶匙／湯匙換算，以及讀取使用者已保存器具。
