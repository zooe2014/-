# 菜就多煉：技術棧與資料設計

## 建議技術棧

| 層次 | 建議 | 理由 |
|---|---|---|
| 後端 API | Python + FastAPI | Python 容易讀寫，FastAPI 適合以型別明確的 API 串接前端；食譜搜尋、條件比對與排序可留在可驗證的程式規則中。 |
| 資料庫 | SQLite | 單一資料庫檔案、無需額外資料庫伺服器，適合此專題規模與本機展示。Python 的 `sqlite3` 可直接連線，不必先加入 ORM。 |
| 前端（後續階段） | HTML、CSS、原生 JavaScript | 簡單頁面不必先引入大型框架；以 `fetch` 呼叫 API。這次不建立完整前端。 |
| 資料交換 | JSON | API 回應使用 JSON；資料庫仍用關聯式表格及外鍵維持一致性。 |
| 食譜推薦 | SQL 檢索 + 明確比對規則 | 以現有食譜資料、使用者勾選、器具適用性和偏好分數排序；不使用 AI 即時生成食譜。 |

SQLite 是單檔、免獨立伺服器的資料庫；Python 標準函式庫提供 `sqlite3` 介面。FastAPI 官方文件將其定位為基於 Python 型別提示的 API 框架。這組合適合快速建立可展示的資料庫檢索原型。[SQLite](https://www.sqlite.org/about.html) [Python sqlite3](https://docs.python.org/3/library/sqlite3.html) [FastAPI](https://fastapi.tiangolo.com/)

### 何時再升級

若之後需要多人同時大量寫入、雲端部署或正式帳號管理，再評估 PostgreSQL、資料遷移工具與登入機制。現階段先不加上 ORM、Redis、AI API 或大型前端框架，以免增加設定負擔。

## 類別圖與資料表對應

原始 UML 類別圖包含「使用者、個人偏好設定、食譜、食材、調味料、推薦比對模組」。本資料模型保留這些概念，並將清單拆成關聯表：

- 使用者與個人偏好設定：`users`、`personal_settings`（一對一）。
- 使用者常備器具：`equipment`、`user_equipment`（多對多）；食譜需求亦使用 `recipe_equipment`。
- 食譜及組成：`recipes`、`recipe_ingredients`、`recipe_seasonings`、`recipe_steps`。
- 替代食材：`ingredient_substitutions`。
- 收藏：`recipe_favorites`（以使用者與食譜的複合主鍵避免重複收藏）。
- 一次搜尋的選取條件：`search_requests` 及其食材、調味料、器具關聯表。
- 推薦比對模組是執行資料庫檢索及排序的應用邏輯，不是另一張資料表；排序規則應固定、可說明、可重現。

## F01–F13 對應

| 需求 | 資料支援 |
|---|---|
| F01 個人口味 | `personal_settings.taste_level`、`eats_spicy`、`default_servings`；推薦與調味份量計算讀取這些欄位。 |
| F02 烹飪器具 | `equipment`、`user_equipment` 儲存器具目錄及使用者常備器具。 |
| F03 查詢食材清單 | `ingredients` 以名稱、分類、別名查詢；`seasonings` 以名稱、分類查詢。 |
| F04 選擇現有食材 | `search_request_ingredients` 保存單次搜尋所勾選的食材。 |
| F05 選擇現有調味料 | `search_request_seasonings` 保存單次搜尋所勾選的調味料。 |
| F06 選擇料理類型 | `search_requests.cuisine_filter` 支援 `any`、`chinese`、`western`。 |
| F07 食譜條件比對 | 比對搜尋條件與食譜組成表；器具需求按 `requirement_group` 分組，每組可用一件符合器具。 |
| F08 推薦結果排序 | 根據必要食材符合度、調味料齊全度、器具適用性計算可解釋分數；分數屬執行時計算，不寫死在食譜資料。 |
| F09 顯示缺少材料 | `recipe_ingredients.is_required`、`recipe_seasonings.is_required` 區分必要與可省略項目；與搜尋勾選清單差集即為缺料。 |
| F10 食譜詳細資訊 | 食譜、食材、調味料、器具及步驟分別存放並以外鍵關聯。 |
| F11 精準調味建議 | 基礎份量、文字十進位數量、單位與偏好設定可供後端以 `Decimal` 計算。克與體積互換須有對應品項的可靠密度；資料不足就不換算。茶匙及湯匙以 5 mL 與 15 mL 為體積基準。 |
| F12 食材替代建議 | `ingredient_substitutions` 明確記錄原食材、替代食材及適用說明；無登錄即不建議。 |
| F13 收藏食譜 | `recipe_favorites` 儲存使用者與食譜的對應，並記錄收藏時間。 |

## 用量與精度

`quantity_value` 與 `grams_per_ml` 使用文字欄位保存十進位字串，應用程式讀取後用 Python `Decimal` 計算，避免先轉成二進位浮點數。食譜保留原始數量和單位。體積單位間可依 1 tsp = 5 mL、1 tbsp = 15 mL 換算；重量與體積之間只有在該品項有經確認的密度資料時才顯示換算值。測試資料未提供經查證的密度，因此不假設克數與毫升可互換。

建議份量與口味計算：先以 `原始用量 × 目標份數 ÷ 食譜基礎份數` 換算份量；若該調味列 `taste_adjustable = 1`，再乘口味係數（初版可採清淡 0.8、適中 1.0、重口味 1.2，之後由實際試做調整）。只在最後顯示時依單位設定精度，不覆寫資料庫原始用量。辣味開關應只影響資料中明確標示為辣味的項目；食譜未含辣味材料時不額外添加。

## 建置資料庫

使用 Python 內建 `sqlite3` 執行 `database/schema.sql`，再執行 `database/seed.sql`。兩個 SQL 檔均設定外鍵；食譜資料的用量是示範資料，實際料理前仍應由專題成員覆核。
